# 目視指摘3点の共通フロー修正

## 問題と原因

1. `citation_style=none` の執筆処理は指示を何も出していなかった一方、共通の根拠採用ルールには「既定の注釈に時点・出典・条件を反映」と書かれていた。内部で区別すべき確認日／適用開始日、出典の採用経緯が本文へ漏れていた。
2. サービス配置は `comparison_featured` として1位・強い推奨を指定していたが、契約要件と網羅性検査では、機能を読者のメリットへ変換し、冒頭・個別紹介・まとめで第一候補として勧める理由を明確に検査していなかった。整合性検査の例も「数値を公表しているから選ぶ」という弱い説明へ誘導していた。
3. 複数商品の比較は表とする規定はあるが、個別商品紹介の主要情報には表の要件がなかった。一般の箇条書きルールでは通ってしまった。

したがって先の合格判定は、この読者向け提示とCV目的の品質要件を十分に検査できていなかった。事実確認の合格だけで記事目的まで満たしたと扱えない。

## 修正

読者向けの共通基準を `reader_presentation.py` に一元化し、構成・サービス配置・執筆・修正・最終確認へ同じ内容を渡す。既存の矛盾する注釈指示と過度に消極的な訴求例は置き換えた。

- none時は出典一覧・確認日の定型注釈・内部の採用説明を自動出力しない。他の3種類の出典表示設定と参照必須URLの例外は維持。
- 内部確認日と、読者が理解すべき過去の価格時点・統計対象時点を区別。性別・プラン・契約期間などを一緒に消さない。
- CV対象の強み→読者のメリット→第一候補にする理由を、既存の網羅性担当が検査。他社は用途に応じた代替として紹介し、均等推奨は要求しない。
- 会員規模から相手探しの選択肢の広さ、写真ぼかしから身バレへの不安を抑えた利用など、機能の作用に沿ったメリットを許可する。未確認の他社順位、累計を現役会員数とする読み替え、成果や安全の絶対保証は区別する。
- 個別商材紹介には主要情報の表を必須とし、既存の情報整理担当が確認。総合比較表では代替しない。FAQや単なる言及には表を増やさない。構成では列・目的だけを指定し、完成表を生成しない。

追加の品質確認モデル呼び出し・新工程・予算増額はない。テキスト指示は増減するため送信トークンは変わるが、追加API費用はこの作業では0。外部通信を遮断した442件のテスト通過。これは設定伝達・既存の不合格検出・工程の接続の検証であり、新プロンプトの実モデル出力品質の合格ではない。

実装はテストブランチのみ。フロントの完成記事には手編集を反映しておらず、元の監査結果・費用履歴も書き換えていない。提示基準の変更後は過去の合格を自動流用しない。保存済み調査のポリシー照合にも影響があるため、旧ジョブをそのまま有料再開せず、必要工程・費用を先に見積もる。別記事テストは保留を維持。

## 追加：深掘り検索意図との接続を商材共通にする

機能→直接のメリットに加え、読者の望み・回避したいこと・守りたいものの葛藤に接続する。指定商材を中心に訴求し、未指定なら根拠あるランキング上位・主要推奨候補へ重点配分する。ランキングがない記事に新しい順位を作らない。感情的な接点が薄い検索では無理に葛藤を作らず、主要情報の後などに自然に配置する。CVR向上は目的であり実測済み効果ではない。

既存 `intent_chains` は origin / direction / trace / concrete_phrase を持つが、専用の執筆補助では例文と方向だけを渡していた。共有の投影処理で起点と深掘りの軌跡も構成・執筆へ渡す。最終確認では既存の網羅性担当だけが同じ文脈を読み、該当する不足の修正時にも引き継ぐ。他担当へ調査資料を一律に増やさない。元の検索意図本文も従来どおり執筆で参照する。

「話し相手はほしいが、家庭や子どもの将来への影響は避けたい。そのジレンマに応える機能」という表現は読者の願望と機能を結ぶもので、家庭や将来が必ず守られるという結果保証と区別する。便益を弱める免責の自動付加は要求しない。

外部通信なし444件通過。転職・時短家電・交流サービスの例について、例文がなくても起点とtraceを保持すること、保存済み分析が最終確認へ入り、その文脈は網羅性担当へ限定されることを検証。新しい実モデル生成は未実施。課金・本番反映・既存記事の手編集なし。
