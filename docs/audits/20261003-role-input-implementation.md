# 2026-10-03 担当別の入力整理と事実照合の振り分け

## 今回実装した範囲

合意した3点をテストブランチの本体へ接続した。別の生成フローを増やす変更ではなく、既存の確認・修正工程へ渡す入力とモデルの振り分けを変更している。
有効条件は既存と同じ `ARTICLE_REVIEW_PROVIDER=tiered` と `QUALITY_RESEARCH_ROUTING=focused`。本番設定、フロント、保存済み記事には反映していない。

### 1. 構成・網羅性向けの入力

- 全質問ID・重要度・回答・採用条件・適用時点・現在の結論への使用可否・未確認／省略状態・省略理由を維持する。
- 引用原文の重複と調査時の探索説明を、担当へ渡す複製から外す。保存された調査台帳・引用・原資料自体は変更しない。未知の追加条件フィールドも削らない。
- 構成確認は、すでに調査確認で採用した回答・条件と構成の主張をSolが照合する。原文を毎回読み直さない。事実上の指摘が出た場合だけ原文照合へ回す。
- その原文照合が合格しても、別項目の網羅性・整合性の不合格は消さない。既存の全確認項目を維持する。

### 2. 完成記事の原文照合

- Lunaが記事全体と取得原文を読む。事実照合、網羅性、文章、全体整合性、情報整理の5担当は維持する。
- 不合格、不確かな判断、複雑な比較や適用条件等の追加確認をSolへ回す。
- 「唯一・最多・最安・No.1・他社より」等の比較断定は、Lunaの合格だけで独立確認を省略しない。決定的な抜き取り確認も残す。
- Solには対象段落、その前後、記事の見出し、関連資料を提示する。保存資料の一覧と版の識別値を付け、必要なら一度だけ資料範囲を広げる。資料を選べないときは全資料へ戻す。
- なお未確認なら不合格のまま。モデルが示した段落IDや資料URLが不正なら受け付けない。
- 同じ要求は既存の応答保存を再利用し、同じ費用台帳で上限を確認する。新しい台帳や予算を作らない。

### 3. 本文修正向けの入力

- 文章・重複・長い文章の連続だけの修正では、取得原文と調査台帳を再送しない。記事全体、確認済み事実、条件、ユーザー設定、構成上の要件は維持する。
- 事実修正は、Solが実際に確認した資料・段落の記録があり、対象段落と資料版が一致する場合だけ、その資料へ絞る。
- 記録がない、資料が変わった、未確認、別の構造上の問題もある場合は全資料を残す。文字列の類似だけで根拠を推測して削らない。
- 修正後の機械検査・5担当の再検査・最後の完了判定は維持する。

## 検証

ネットワーク禁止の342テストが合格。

- 全質問・回答条件・ユーザー設定の保持、元の台帳を変更しないこと。
- 5担当と全文確認の維持、構成確認の全項目の保持。
- 構成の事実上の指摘だけが原文照合へ進み、別の不合格は残ること。
- Lunaの不合格・追加確認要求・比較断定・抜き取りからSolへ進むこと。
- 資料追加は一度までで、不明や不正な参照を合格にしないこと。
- 資料版・確認対象が一致しない修正では入力を狭めないこと。
- 予算を使い切った同じジョブでは、HTTP送信前に停止すること。

監査の版とスナップショットへ新しい振り分けを含め、旧仕様の判定を新仕様の合格として流用しない。
実モデルの判定精度、通常生成した記事の完成品質は、この自動テストで証明していない。
