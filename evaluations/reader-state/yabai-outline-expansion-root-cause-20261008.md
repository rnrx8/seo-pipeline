# 構成・本文の膨張原因の追跡（2026-10-08）

対象: 隔離テスト 92053d25-779e-4a05-a224-66df896ff56f。追加API呼び出し・本番変更なし。
実行成果物: /Users/ryoka/seo-saas/tmp/yabai-article-preflight/artifacts。

## 確認済みの因果経路

1. SERP上位ページから、script/style/nav/footer/headerを除いたbody全体の非空白文字数を取得する。記事本文だけを識別する抽出ではない。取得成功9件から最小1件・最大1件を除外し、残り7件の平均12,132.142857字を算出。Yahoo!知恵袋も対象に入っている。実ページの余分な要素が何字混入したかは今回未測定。
2. 平均×1.2=14,559字、平均×1.3=15,772字。競合参考値を「確定値」と指示し、job.word_count_settingへ保存する。後工程ではユーザー指定と自動算出の出自が区別されない。
3. 構成プロンプトは、H2配分合計を目標文字数に一致させる。構成の最初のH2は概要・後続章案内・利用経験調査を指示する一方、H3を設計せず1,600字を割り当てる。「直接回答→概要一覧→後続詳細」の役割と、独立した3論点の説明範囲が明確に区切られていない。
4. 構成確認は事実・比較条件・重要論点を評価し、prose_quality/redundancyはresearch段階ではnot_applicable。現物も両項目がnot_applicableでpass。構成上の表示設計・冗長さ・説明範囲と分量の整合性を具体的に確認した記録はない。
5. 第1パートの目標は1,600+2,000+2,200=5,800字。validate_deliveryに5,800字を渡し、その80%=4,640字を機械的下限にする。第1回は4,123字。落とした理由はarticle_too_shortのみで、具体的な未回答項目は提示していない。
6. 再生成指示は「以下の欠落・不備を修正し、このパート全体を再出力」「未執筆の解説を補完する」とissue JSON。issueのreasonは「構成の説明不足を補完する」。章候補の選択・優先順位・追加可否を決めるコードはない。モデルに本文全体の再出力を任せる。
7. 第1回から構成外のH3「3つの理由はどの章で詳しく分かる？」「既婚者のマッチングアプリ利用経験は15%という調査がある」が存在。第2回で「不貞行為・金銭被害・身バレは、それぞれどう『やばい』のか」が追加。第1H2は1,076→1,738字、パートは4,123→5,247字。検査は第2回をvalid=trueとした。

モデルの内部判断は観測できない。文字数再生成だけが全ての見出し追加の原因とは言えない。初回の構成外H3と、文字数不足再生成時の追加H3を分けて扱う。

## 同系列で確認した設計上の問題

- 配分表の自動補修は、タイトルに比較/おすすめ/ランキングがあると重み5、それ以外4を使い、H3数で残余目標を配分する。実際の検索意図優先度を読まない。今回はmetaのvolume_design_repaired=falseであり、この補修を今回1,600字配分の直接原因とはしない。
- 調査計画のessential/important/supportingは資料に渡るが、パート再生成は未回答質問のIDに結び付けられていない。
- 構成局所修正は見出し追加・削除・移動・階層変更禁止。章の分け方に問題がある場合、言い換えだけでは直せない。
- 校閲にも文字数不足から「未執筆項目を補完」と要求する処理があり、パート生成だけ直すと後で同じ要求が復活する。
- CV指定からリード推薦を要求した別の不整合もあり、文字数原因とは別に修正する。

## 修正の境界

1. ユーザー指定の量と競合参考量の出自を保持。競合量は重要論点の網羅を設計する参考にし、機械的な本文不足・有料再生成の理由にしない。
2. 構成は、章の読者の疑問、回答要素、子節への割当て、後続詳細との境界、根拠を具体的に設計。分量を満たすための追加章は作らない。
3. 既存の構成確認の中で、論点の分け方・案内章の不要な独立・補足を詰め込んだ見出し・分量との整合性も評価する。確認呼び出し数は増やさない。
4. 内容不足は未回答の必須・重要論点を特定して補完。説明項目がそろって短い場合を「未完成」としない。低優先度の補助候補は空いた文字数だけを理由に追加しない。
5. 章構造の変更は構成側の修正として扱い、構成と本文と検査対応を同じ版へ更新。通常の本文局所修正の中で勝手に章を増減しない。
